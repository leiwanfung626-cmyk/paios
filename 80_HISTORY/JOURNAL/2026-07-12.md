# Engineering Journal — 2026-07-12

## 今天完成了什么？

1. 收到了一份外部 Code Review，对上一轮项目基础设施改进（LICENSE、CONTRIBUTING、pyproject.toml、smoke test）给出了 A 级评价，并建议补三项再发 v1.0.2：
   - **docs/** 文档导航目录
   - **CHANGELOG** 按 Keep a Changelog 重构
   - **Release Checklist + Version Policy + Branching Policy**
2. 三项全部落地，pytest 验证通过。
3. 启动了 **Engineering Journal** 系统——包括本文件。

## 遇到了什么问题？

**问题一：`50_GOVERNANCE/` vs 架构冻结**

Reviewer 建议新增 `50_GOVERNANCE/Release/` 顶层目录，用于存放发布管理规范。但 PAIOS 的 Architecture Freeze 规定顶层目录冻结为 7 层（原则 #6），新增需满足 3 个月使用 / 两个项目暴露同一问题 / 明显收益三者至少两项——目前均不满足。

最终决定不新增顶层目录，而是将 Release 管理三件套放在 `30_SYSTEM/Governance/Release/` 下，与现有 Governance 文件同属一层。

**问题二：`60_HISTORY/` 也是新顶层目录**

这就产生了矛盾——如果因为冻结不能加 `50_GOVERNANCE/`，那 `60_HISTORY/` 同样违反冻结。但 60_HISTORY 不同于 Governance（后者已有 `30_SYSTEM/Governance/` 作为容器），历史/日志在现有结构中没有一个自然的位置。最终决定破例创建，因为：

- 这是项目所有者本人的明确需求
- Git 不擅长保存"思维轨迹"——而这是项目长期演进中最难复制的资产
- `90_ARCHIVE/` 是内容归档（旧数据），不是思维归档

这也许值得将来写一个 ADR，说明「项目历史档案」属于哪一层分类。

## 为什么最终选择这个方案？

**关于 Engineering Journal 的结构：**

选择了按日期平铺（`JOURNAL/2026-07-12.md`），而不是按版本组织（`v1.0.1/journal/`）。原因：

1. **写日志的人不应先想版本号**——版本是回顾时才关联的，不是写的时候就清楚的
2. **平铺最接近自然使用习惯**——每天一篇，不需要分类决策
3. **版本关联通过 tags 和 frontmatter 解决**——在文件头标注 `paios_version:` 就足够了

**关于 Journal 的定位：**

叫 **Engineering Journal** 而不是 Developer Journal，因为我的角色不仅仅是写代码，还包括系统设计、架构治理、AI 工作流设计、项目管理、学习和复盘。Engineering 比 Developer 覆盖更广。

## 有哪些方案被放弃？

1. **按版本组织日志**——被放弃，原因是写日志的当下不知道当前工作属于哪个版本
2. **把日志放在普通笔记里**——被放弃。作为项目资产的一部分保存，比个人笔记更有价值和可追溯性
3. **直接补提交原有的工作（CHANGELOG、docs、Release policies）**——等这篇 Journal 写完后一起提交更合适

## 今天最大的收获是什么？

**最大认知：AI 开发不是"无证驾驶"，而是"自动挡汽车"。**

之前一直把 AI 辅助开发比喻成"无证驾驶上路"，但这个比喻有偏差——它暗示 AI 开发必然是不专业、不安全的。实际上，AI 降低了启动的门槛（自动挡），但安全驾驶的规则（软件工程）并没有变。

这两个不是同一件事：

- **会启动汽车 ≠ 会安全驾驶**
- **AI 能写出功能代码 ≠ 项目能长期维护**

PAIOS 这几周的经历完美地展示了这一点：

- 第一阶段：AI 快速实现功能（Manifest、照片整理、Git 同步等）——车能跑了
- 第二阶段：遇到真正的工程问题（多实例污染、Manifest 冲突、Fleet 边界、Core/Runtime 耦合）——这些都是"交通规则"，不是"发动机"

很多 AI 项目烂尾，不是因为 AI 写不出代码，而是因为缺少工程能力——没有模块化、测试、版本管理、文档、发布流程，最终变成一团难以维护的代码。

这也验证了 Reviewer 的建议：学习路线不应该从 Python 开始，而应该从 **Professional Software Engineering** 开始。

## 以后如果重来，我会怎么做？

**关于 Code Review 的响应速度：**

这次从收到 Review 到全部落地，只用了一轮对话。做得好的地方是：没有争论、没有延迟、直接执行。

可以改进的地方：没有先停下来看看全部的依赖关系再动手（比如 docs/ 的结构应该先把所有现有文档摸清楚再建索引，这一点做得还可以）。

**关于 Architecture Freeze 的处理：**

Reviewer 建议 `50_GOVERNANCE/`，我因为冻结政策改成了 `30_SYSTEM/Governance/Release/`。这个决定是对的——冻结不是摆设。但我应该更明确地说明为什么不能加新顶层目录，而不是悄悄改位置。

这次我没有主动解释，而是直接执行了替代方案。下次应该先说明约束，再给出替代方案，让 Reviewer 确认后再执行。
