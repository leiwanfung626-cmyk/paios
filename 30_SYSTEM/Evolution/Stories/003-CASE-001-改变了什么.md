# Story-003: CASE-001 改变了什么

> **时间线**：2026-07-10 ~ 2026-07-11
> **关联**：`30_SYSTEM/Evolution/Case-Studies/CASE-001-Multi-Instance-First-Convergence.md` · `30_SYSTEM/ADR/ADR-0017` · `ADR-0018` · `30_SYSTEM/Governance/Architecture-Lifecycle.md`
> **状态**：定稿

---

## 事件回顾

CASE-001 是 PAIOS 第一次真实多实例并流事件。

当三个实例（Case-01 工作、Case-02 个人、Case-03 考研）第一次同时在线并尝试同步时，立刻暴露了三个结构缺陷：

1. **Manifest 单路径冲突**：三个实例都往 `PAIOS-Usage/manifest.yaml` 写——远端被 Case-03 覆盖
2. **Fleet 双位置并存**：仓库内 `F:\PAIOS\Fleet\cases\` vs 仓库外 `F:\Fleet\`——语义冲突
3. **Workspace 泄漏进 Core**：考研知识库被推入共享仓库

## 最初的判断

事件发生后，第一反应是修复。

最初的思路是战术性的：修复 manifest 路径、统一 Fleet 位置、清理 Git 历史。

但讨论中一个更根本的问题冒出来了。

## 真正的发现

> **三实例同权——都以 Developer 运行——是根因。**

不是"某人手滑"，不是"Git 操作不当"，而是**权限模型错了**。

如果三个实例都是 Developer，都能写 Core，那不管加多少规则，污染都只是时间问题。

## CASE-001 引发的连锁反应

CASE-001 不是被当作"一个 bug 被修掉了"，而是被当作**架构证据**——它证明了 Phase A 的设计在多实例场景下存在结构性缺陷。

它触发了完整的 Architecture Lifecycle：

```
CASE-001（证据）
    ↓
ADR-0017（平台纯度 — 内容分离）
    ↓
Phase B 蓝图（Core/Workspace 拆分方案）
    ↓
Governance 层抽离（Lifecycle / Change Control / Decision Traceability）
    ↓
Architecture Lifecycle v1.0 冻结（治理框架制度化）
    ↓
ADR-0018（角色模型 — Developer/User 分离）
    ↓
边界建立（Phase B Step 2）
    ↓
用户侧 SOP（面向 Case-02/03 的铁律和日常操作）
```

## 认知转折

CASE-001 最大的改变不是修了什么，而是**让 PAIOS 从"有治理"变成了"治理驱动"**。

之前：治理是锦上添花——有空就写写 ADR
之后：治理是平台基线——没有治理，多实例无法运行

Evidence-Driven Evolution 这个治理方法论就是在这个时候确立的——不是"想好了再做"，而是"用真实运行证据驱动架构演进"。

## 被放弃的方案

| 方案 | 为什么放弃 |
|------|-----------|
| 立即修 Manifest 路径 | 治标——根因是权限模型，不是路径 |
| 直接做 Core/Workspace 物理拆分 | 风险大——没有治理基线就动手，会引入新问题 |
| 让三个实例协商文件写入顺序 | 复杂度高，且无法扩展到更多实例 |

## 认知总结

> **CASE-001 真正的价值不是暴露了 Bug，而是暴露了 PAIOS 还没有准备好管理多个实例。**

这次事件之后，PAIOS 的架构假设发生了根本变化：

- 之前：多实例只是"多人用同一套系统"
- 之后：多实例需要"角色模型 + 数据流边界 + 单向同步 + 治理闭环"

这才是 CASE-001 最深远的影响——它把 PAIOS 从一个工具变成了一个平台。
