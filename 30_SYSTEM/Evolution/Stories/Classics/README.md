# Classics — PAIOS 建国史·必读五篇

> 无论你是新加入的 Contributor、未来儿子、还是未来 AI，
> 第一次理解 PAIOS，都先读这五篇。
>
> 它们不是规范，不是 SOP，不是 ADR。
> 它们是 PAIOS 架构思想形成的故事——系统最独特、也最难复制的资产。

## 必读清单

| # | Title | 为什么必读 |
|---|-------|-----------|
| **001** | [为什么 PAIOS 不是第二大脑](../001-为什么PAIOS不是第二大脑.md) | PAIOS 的起源——从"AI 知识库"到"操作系统"。读完这篇才能理解 PAIOS 为什么不是又一个 RAG 项目。 |
| **002** | [Platform Purity 是如何诞生的](../002-Platform-Purity-是如何诞生的.md) | 核心架构原则的诞生过程——为什么 Workspace 进入 Platform 不是操作失误，而是架构上没有边界。 |

| **004** | [Need Driven Promotion 的来源](../004-Need-Driven-Promotion的来源.md) | 不做比做更难。这篇解释了 PAIOS "不做不必要功能"的原则从何而来。 |
| **005** | [为什么不用直接 Merge](../005-为什么不用直接Merge.md) | 多实例不是同步关系，而是 Review → Promote 关系。这篇解释了 PAIOS 最根本的协作模型。 |

## 阅读顺序

建议按编号顺序阅读。五篇之间有内在逻辑：

```
001（哲学）→ 为什么做 PAIOS
    ↓
002（架构）→ Platform 和 Workspace 怎么分
    ↓
003（治理）→ 真实问题如何催生治理
    ↓
004（原则）→ "不做"比"做"更难
    ↓
005（协作）→ 多实例怎么一起工作
```

读完这五篇，你就理解了 PAIOS 的**设计哲学、架构原则、治理逻辑和协作模型**。
