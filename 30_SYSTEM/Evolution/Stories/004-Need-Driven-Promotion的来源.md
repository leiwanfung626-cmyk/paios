> **时间线**：2026-07-01 ~ 2026-07-09（运行验证期逐步形成）
> **关联**：`30_SYSTEM/Principles.md` · `30_SYSTEM/ADR/ADR-0010-Evolution-Strategy.md`
> **状态**：定稿

## 问题的起源

在 PAIOS 的运行验证期，出现了一个反复出现的模式：

每次讨论一个问题，AI（和各种工具）都很喜欢说：

> "这里还能增加 X 功能……"
> "建议加入 Y 模块……"
> "未来可以扩展 Z……"

这些建议本身没有错。但积累多了，问题就出来了——**项目在做加法，但没有人问减法**。

## 最初的原则提炼

在一次讨论中，你提出了一个非常清晰的原则：

> **不要因为能做而去做，只因为需要才升级。**

这句话后来被提炼为 **Need Driven Promotion**。

它背后有两层含义：

```
表层：不要凭想象加功能
深层：功能应该由真实需求触发，不是由技术可能性驱动
```

## 与 Requirement Emergence 的关系

PAIOS 当时已经有一个原则叫 **Requirement Emergence（需求涌现）**——需求不是一开始就明确的，而是在迭代中逐渐清晰的。

Need Driven Promotion 和它是互补的：

```
需求涌现：需求是怎么出现的（认识论）
Need Driven：什么需求值得做（决策论）
```

两者的区别：

| 原则 | 回答 | 应用场景 |
|------|------|---------|
| Requirement Emergence | 需求从哪来 | 设计阶段——不要等完美需求 |
| Need Driven Promotion | 什么时候做 | 决策阶段——不要凭想象加功能 |

## 实际案例

Need Driven Promotion 在 PAIOS 的发展中被反复验证：

| 候选功能 | 结果 | 依据 |
|----------|------|------|
| 图片管理 | 延迟（Case 未触发） | 真正需要时再做 |
| Review 系统 | 观察中（3 例均未启用） | 没有人需要就不建 |
| aggregate.py 自动化 | 延迟到 Phase B 之后 | 先跑通手动流程 |
| Release 机制 | ✓ 立即做 | 多实例需要版本管理 |
| Fleet | ✓ 立即做 | Manifest 需要聚合入口 |
| Pilot Gate | ✓ 立即做 | 架构变更需要验证机制 |

## 被放弃的方案

| 方案 | 为什么放弃 |
|------|-----------|
| 按固定周期发布功能 | 容易产生镀金功能 |
| 收集所有建议再优先级排序 | 没有真实运行数据支撑排序 |
| 一次性做大版本规划 | 违背需求涌现原则 |

## 认知总结

> **"能做"和"该做"是两件事。**

Need Driven Promotion 看起来很简单——少加功能——但它实际上是 PAIOS 治理哲学的缩影：**相信真实运行数据，而不是预测。**

它不是保守，而是对"架构熵增"的防御——不加控制的话，每一个"顺便加一个小功能"都会让系统变得更复杂、更难维护。
